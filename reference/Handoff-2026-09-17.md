## 5. Teaching behavior to retain

Read the latest journal, open issues, curriculum and next plan before the first question. Ask one question, then wait. Test independent recall before providing a model. Use mostly English at first; explain meaning and give Brazilian Portuguese slowly, then at natural speed. Avoid screen dependence, long lists and academic grammar.

Follow answers, not a rigid syllabus clock. Review or simplify when retrieval is weak. A usual successful lesson may introduce one useful sentence pattern and about five words/phrases, but this is a ceiling to adapt, not a quota. Build into short everyday exchanges and finish with a role-play. Permit “slow down”, “five minutes left”, “keep going” and “finish here”. A brief or interrupted lesson must still preserve evidenced work.

Repetition does not count as mastery. Record whether an answer was independent, prompted, repeated, not recalled or unclear. Distinguish isolated meaning-cue retrieval from conversation. Pronunciation may be clear, need work or remain uncertain; do not invent a phonetic assessment from a transcript alone.

Current automatic policy in `applyLesson`: failures or prompts in the current lesson keep a phrase Developing. Clear independent use can make it Functional. Mastery requires evidence across at least two distinct days for isolated retrieval and across at least two distinct days for spontaneous clear conversation, without a current failure. Review the implementation with tests before altering it. Planned phrases must not be marked learned merely because they appear in a plan.

## 7. Existing architecture and API contracts

Frontend is plain ES modules; no framework rewrite is required. Browser WebRTC sends audio to OpenAI. The server creates the call using multipart SDP at OpenAI's Realtime call endpoint and returns the SDP answer; the long-lived API key remains on the server. A separate same-origin authenticated WebSocket connects the browser to the Worker, which opens a server-side connection to the same OpenAI call by call ID.

The server observes usage and tool calls, saves practice checkpoints and controls session lifecycle. The browser microphone and model auto-response are initially held until the saving/control connection is ready. Raw audio is not stored by Fala. Saved evidence includes model-assessed practice checkpoints and assistant text; it is not a guaranteed verbatim human transcript.

Tools: `record_practice`, `set_lesson_time`, `get_lesson_status`, `finish_lesson`. Tool schemas live in `worker/domain.js`. Structured notes are generated after the session with a deterministic fallback if generation fails. Finalization is designed to be retryable and idempotent. It merges through notebook revision checks and retains the previous next plan if no assessed practice exists.

| Method/path | Function |
|---|---|
| POST `/api/bootstrap` | Import a valid legacy notebook once or initialize seed; return notebook and costs |
| GET/PUT `/api/notebook` | Read or save state; PUT includes revision and returns 409 on conflict |
| GET `/api/usage` | Estimated monthly usage, recent sessions, settings and setup state |
| PUT `/api/settings` | Validate model, duration, AUD budget and FX settings |
| POST `/api/voice` | Validate readiness/budget, reserve session, create Realtime call |
| GET `/api/voice/:id/control` | Authenticated WebSocket control and server event observation |
| GET `/api/voice/:id` | Session and saved-checkpoint status |
| POST `/api/voice/:id/finish` | Fallback finish, hang up and finalize |
| POST `/api/voice/:id/retry` | Retry summary completion from saved evidence |

D1 tables: `notebooks`, `settings`, `voice_sessions`, `lesson_events`, `usage_events`. Notebook state is JSON (`schema: 1`) containing `phrases`, `lessons`, `issues`, `curriculum`, `patterns`, `reviews`, `next` and `sources`. Keep IDs stable. The partial unique index prevents more than one starting/active/finishing session per owner. Usage IDs deduplicate API responses.

Local browser state, backups and drafts supplement the server record. Writes use compare-and-swap revision checks; conflicts retain local drafts. Legacy localStorage is per-origin and will NOT move automatically to a new domain. Source inspection is the authority for exact body shapes and response fields.

## 8. Hosting recommendation and required migration work

Use a **private GitHub repository**, **Cloudflare Workers** for the application and WebSockets, **D1** for persistence and **Cloudflare Access** or equivalent verified owner-only authentication. This is an implementation recommendation based on the existing Worker/D1 code, not a claim that a Cloudflare account, domain or plan is already provisioned.

GitHub Pages is a static site service and cannot run this Worker, store server secrets or operate the voice backend. GitHub Actions can deploy Workers. See [GitHub Pages scope](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) and [Cloudflare's GitHub Actions guide](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/).

### Critical: replace the trust boundary before public reachability

`worker/index.js` currently trusts `oai-authenticated-user-id`, supplied by the Sites gateway. Outside Sites, a caller could forge that header. Also, assets are currently returned before the API authorization check because Sites protects the whole site externally. The assets include personal baseline lesson content.

Implement verified authentication for **all pages, JavaScript, JSON and WebSocket endpoints** before exposing the app. With Access, validate the signed assertion, signature, issuer, audience and expiry and enforce Dan's allowlist. Use a stable verified subject for database ownership; never trust a raw email/header or client-supplied owner ID. Protect or disable alternate workers.dev and preview routes too. Retain same-origin and content-type checks. Add tests for forged Sites headers, invalid/expired JWTs, unauthorized users, direct-host bypass and WebSocket authorization. Follow [Cloudflare's JWT validation guidance](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/).

### Build and runtime portability

Add and pin Wrangler; provide a target-host configuration with the Worker entrypoint and a `DB` D1 binding. Obtain the actual database ID from the new account. Point migration tooling at `drizzle/`; do not assume Drizzle generation metadata applies SQL to a database. See [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/).

Adapt `build.mjs` so it no longer requires or publishes Sites metadata. Its current entrypoint output is `dist/server/index.js` with embedded assets. If adding an authentication library, replace the simple string-based concatenation with a proper module bundler; it is not designed to resolve imported third-party packages. Retain the asset mapping or implement an equivalent secure asset-serving path.

Replace the static-only local dev command with a genuine Worker development setup using local D1 and local secrets. Use a current Node version with `node:sqlite` support (for example Node 24, then verify the suite). A successful `npm run dev` today demonstrates only static UI serving.
